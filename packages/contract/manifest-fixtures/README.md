# Manifest 正反样例

**Host（Rust）与 CLI（TypeScript）跑同一批样例。** 这是防止两套校验实现漂移的唯一有效手段——两边都能写得头头是道，但只要对同一份 Manifest 给出不同结论，App 开发者就会遇到「本地 validate 通过、装的时候被拒」，而且看不出是谁错了。

## 目录

- `valid/` —— 必须零告警通过。
- `invalid/<name>.json` —— 必须被拒。
- `invalid/<name>.expected.json` —— 期望的**稳定错误码集合**与这条规则存在的理由。

```json
{
  "codes": ["HOST_CAPABILITY_NOT_AVAILABLE"],
  "note": "首版没有 Network Broker，插件一律禁网"
}
```

## 断言方式

比对的是**去重后的错误码集合**，不是错误条数，也不是错误文案：

- 条数会随实现细节变化（同一个问题报一条还是两条），不该让测试红；
- 文案要能随时改进措辞；
- 错误码是对外合同，改它就是改协议——这才是该锁住的东西。

每个反例只违反一条规则，因此集合通常只有一个元素。

## 加新规则时

1. 在 `invalid/` 加一组 `.json` + `.expected.json`；
2. 两侧实现都改；
3. 两侧的 fixture 测试都会跑到它——漏改哪边，哪边红。

`.expected.json` 里的 `note` 不是注释，是**这条规则为什么存在**。三个月后有人想放宽它时，这句话是唯一能回答「当初为什么要拦」的东西。
