## 根因核对

原测试在挂载前建立 `Date.now() + 60` 的到期时间。生产挂载先等待适配器快照，再进行首次分类；`visibleTransientStatus` 对 `expiresAt <= now()` 返回空。挂载耗时超过 60 毫秒即可在首次断言前产生「全部 · 6」。这与同轮报告记录的 CI 失败位置和实际值吻合。源码没有给出需要修改生产 TTL 的证据。

## 最终差异核对

- 协议时钟固定，只有测试明确到期时才推进到 `deadline + 1`。快照延迟 0/120 毫秒覆盖正常挂载和超过原 TTL 的挂载。
- 测试捕获并转发真实 `setTimeout`，保留真实 handle，并要求安排 61 毫秒闹钟；测试调用的是捕获的生产回调。
- 到期测试保留「工作中 · 1、全部 · 5」到「全部 · 6」的业务断言，没有通过其他状态事件触发重绘。调用回调前清除 native handle，避免重复执行。
- dispose 测试严格要求 `clearTimeout` 清除本次到期 handle，并执行迟到回调，检查卸载后会话组和会话项仍为空。
- helper 的 `finally` 无条件恢复全局 `setTimeout`；dispose 用例的 `finally` 恢复 `clearTimeout` 后再次清理 view。主断言失败也会清理 view。
- 没有改动生产代码、TTL、公开 API 或其他项目。
